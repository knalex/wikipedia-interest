# Інтерес до тем у Вікіпедії — навичка для AI-агента

Навичка у форматі [Agent Skills](https://agentskills.io/specification), з якою
агент аналізує статистику переглядів Вікіпедії, будує графіки та готує короткі
звіти. Звіти допомагають командам B2C-продуктів вирішити, які теми розвивати і
якими мовами запускатися. Повний опис завдання — у [task.md](task.md).

Проєкт робиться поетапно, і кожен етап перевіряється окремо. У цьому файлі
описано, що зроблено і як це перевірено.

## Структура

```
.

    │   └── output_files.py       # тека результатів wikipedia-interest-output/ і перелік файлів
    ├── assets/fonts/             # DejaVu Sans (кирилиця) і її ліцензія
    ├── tests/                    # офлайн-тести і записані відповіді API
```

## Етап 1: визначення теми

### Навіщо він потрібен

Pageviews API рахує перегляди окремої статті за її точною назвою. Назви
статей рідко збігаються з дослівним перекладом. Якщо назву вгадати
неправильно, API повертає порожній ряд, і це легко сплутати з «інтересу
немає». Етап 1 знімає це вгадування: з фрази користувача він дає точний
перелік статей для кожного мовного розділу.

### Як це працює

Скрипт іде через **Wikidata**, де одне поняття (QID) пов'язане зі статтями в
усіх мовних розділах. На виході — «кошик теми»: основне поняття, статті та їхні
перенаправлення по мовах, а також ширші й вужчі поняття, які можна
запропонувати користувачу.

Основні рішення:

1. **Спершу поняття, потім статті.** Агент передає слова користувача і
   англійське формулювання (`--query uk:... --query en:...`). Перемагає
   поняття, на якому сходяться кілька формулювань. Далі — точна назва краще
   за збіг за початком. Нічию розв'язує лише перевага в 3 рази за кількістю
   мовних розділів зі статтею, інакше статус `ambiguous` і питання
   користувачу.
2. **Пов'язані поняття ніколи не додаються мовчки.** Ширші поняття (для
   інтервального голодування — «піст») і вужчі (для астрономії —
   астрофізика, космологія…) лише пропонуються. Додаються вони через
   `--include` або `--scope extended`.
3. **Перенаправлення рахуються.** Pageviews зараховує перегляди
   перенаправлення його власній назві, тому в кошик потрапляють і вони.
4. **Якщо статті немає, це факт, а не нуль.** Для таких розділів скрипт шукає
   сторінки з точно такою назвою і згадки фрази в інших статтях. Знахідки
   йдуть як докази для користувача, у підрахунок вони не потрапляють.
5. **Агент не вирішує за користувача.** Якщо значення визначили формулювання
   агента, а не слова користувача («Меркурий» → «Mercury (planet)»), скрипт
   готує уточнювальне питання першим пунктом `next_steps`. Те саме, якщо
   фраза користувача — лише прізвище.
6. **Помилки розрізняються.** Неіснуючий мовний розділ (`tlh`) повертає
   `unknown_wikipedia_edition`, а не мережеву помилку. Мережева помилка
   нічого не каже про тему.
7. **Усе, що бачить агент, — українською,** відповідь користувачу теж.
   JSON-ключі, статуси та коди попереджень лишаються англійськими: це
   контракт для наступних етапів.

### Приклад

Запит із завдання: *«Порівняй зростання інтересу до інтервального голодування
в польськомовній та чеськомовній Wikipedia за останні два роки».*

```bash
cd skills/wikipedia-interest-analysis
WIKIPEDIA_RESOLVER_CONTACT="you@example.com" python3 scripts/resolve_topic.py \
  --query "uk:інтервальне голодування" --query "en:intermittent fasting" \
  --targets pl,cs \
  --user-message "Порівняй зростання інтересу до інтервального голодування в польськомовній та чеськомовній Wikipedia за останні два роки." \
  --out basket.json
```

Скорочений результат (повний — у [`examples/01_intermittent_fasting.stdout.json`](../examples/01_intermittent_fasting.stdout.json)):

```json
{
  "status": "partial",
  "core": {"entity_id": "Q1666254", "label": "Інтервальне голодування", "language_editions_with_article": 31},
  "coverage": {
    "pl": {"core_title": null, "broader_with_article": [{"entity_id": "Q44602", "label": "піст", "title": "Post"}]},
    "cs": {"core_title": "Přerušovaný půst", "included_articles": 1, "included_redirects": 0}
  },
  "warnings": [{"code": "core_missing"}, {"code": "asymmetric_basket"}],
  "next_steps": [
    "Відповідай користувачу українською, навіть якщо він писав іншою мовою.",
    "Перевір, що --targets (pl, cs) — це саме ті мовні розділи, які назвав користувач, без пропусків; якщо чогось бракує, перезапусти з повним списком.",
    "Скажи користувачу: у pl.wikipedia немає статті про «Інтервальне голодування» (Q1666254).",
    "За бажанням переклади тему мовою pl і перезапусти, додавши --query pl:<фраза>.",
    "Запропонуй ширше поняття Q44602 «піст» (pl: Post) через --include Q44602; попередь, що воно ширше і це не та сама тема."
  ]

```

Висновок для користувача: у польській Вікіпедії немає окремої статті про
інтервальне голодування. Фраза «post przerywany» трапляється лише всередині
3 інших статей. Тому пряме порівняння неможливе. Можна рахувати лише чеську
статтю або перейти до ширшої теми «піст», але тоді треба чесно сказати, що
порівняння нерівноцінне.

Усі 21 приклад (приклади із завдання, неоднозначності, неіснуючий розділ,
вигадана тема, опечатка, переклад ширшим поняттям, подія 2026 року) з
запитами користувачів і командами — у
[`examples/README.md`](../examples/README.md).

### Запуск

- Потрібен лише Python 3.8+, залежностей немає.
- Мережа потрібна для `www.wikidata.org` і `<мова>.wikipedia.org`.
- `WIKIPEDIA_RESOLVER_CONTACT` — email або URL для заголовка User-Agent, як
  вимагає політика Wikimedia. Без нього скрипт не запускається.
- Статуси, поля та правила для агента описано в
  [`SKILL.md`](../SKILL.md).

## Етап 2: збір переглядів

`scripts/fetch_pageviews.py` бере кошик етапу 1 і для кожної статті та її
перенаправлень отримує перегляди з Wikimedia Pageviews API. Потім складає по
кожному мовному розділу ряд за місяцями (або днями) і суму за період.

Рішення, які ми перевірили на реальних відповідях API:

1. **Лише люди:** `agent=user`, без ботів; усі платформи (`all-access`).
2. **Поточний неповний місяць відкидається.** API повертає його частково
   (для Bitcoin у вересні 2026 року — 89 тис. переглядів за 27 днів), і графік
   хибно «падав» би в кінці. Для відносних періодів агент передає `--last N`, а
   скрипт сам бере останні N завершених місяців.
3. **Дані є лише з 1 липня 2015 року.** Період до цієї дати скрипт обрізає з
   попередженням. Якщо весь період раніше, повертає помилку, а не порожній графік.
4. **Нулі — це нулі.** Місяці без переглядів API не повертає, а на відсутню
   сторінку чи період без даних відповідає 404. Скрипт заповнює такі місяці
   нулями й позначає статті без переглядів і статті, що з'явилися посеред
   періоду (`series_starts_late`), щоб ріст від нуля не видавали за
   зростання інтересу.
5. **Кеш.** Відповіді за завершені періоди зберігаються в
   `~/.cache/wikipedia-interest-analysis`. Повторний чи пов'язаний запит
   (наприклад, «додай словацьку») не ходить у мережу вдруге: для кави у трьох
   мовах це 0,06 с замість 1,9 с.
6. **Без висновків — готовим текстом.** Етап 2 дає лише дані й суми. Чи росте
   інтерес і наскільки цьому довіряти, оцінює етап 3. Скрипт сам складає
   відповідь користувачу (`summary_uk`): тема, період, суми по мовах, усі
   попередження й застереження, що абсолютні числа різних мов не порівнюються.
   Агент переказує її дослівно, а помісячного ряду в stdout немає. Так ми
   прибрали головний збій раунду 15: коли Haiku бачив 24 числа, він у 11 з 51
   прогону сам «знаходив» спад чи рекомендував аудиторію.

```bash
python3 scripts/fetch_pageviews.py --basket basket.json --last 24 --out views.json
```

## Етап 3: тренд, довіра, графік

`scripts/analyze_trend.py` бере ряди етапу 2 і відповідає на головне питання
завдання: чи зростає інтерес і наскільки цьому можна довіряти. Мережа не
потрібна, залежностей немає: графік — SVG, згенерований стандартною
бібліотекою. Агент лише переказує готовий текст `summary_uk`, тож висновки
завжди однакові для однакових даних.

1. **Рік до року.** Останні 12 місяців порівнюються з попередніми 12, тож
   сезонність (напр., вересневий пік «Астрономії» з початком навчального року)
   не спотворює висновок. Для коротших рядів — дві половини періоду з
   попередженням, що сезонність не врахована. Поріг «без явної зміни» — ±10 %,
   змінюється через `--growth-threshold`.
2. **Поправка на всю Wikipedia.** Етап 2 бере загальну відвідуваність кожного
   розділу. Це виявилося важливим: за останній рік уся uk.wikipedia втратила
   25 % переглядів людей, pl — 9 %, en — 7 %. Кава в польській −18 %, але з
   поправкою лише −10 %, тобто на рівні всього розділу.
3. **Довіра** (висока / середня / низька) з переліком причин:
   - мало переглядів (у середньому менше 100 на місяць) → низька;
   - стаття з'явилася посеред періоду → низька;
   - висновок тримається на одному сплеску (без нього вердикт інший) → низька;
   - різкий і стійкий злам рівня → середня, з проханням перевірити історію
     статті (так виглядають перейменування й перенаправлення);
   - порівняння періодів і стійкий до викидів нахил (Тейла — Сена) вказують у
     різні боки → середня;
   - короткий період без сезонності → середня.
4. **Порівняння мов** — лише за відносною зміною з поправкою на розділ, не за
   абсолютними числами. Різниця менша за поріг — «динаміка однакова»; лідер із
   низькою довірою — «висновок про лідера ненадійний».
5. **Графік.** Одна мова — перегляди; кілька — індекс (попередній період =
   100), щоб мови з різною аудиторією були на одній шкалі. Сплески й злами
   позначено, період порівняння затінено.

Приклад для астрономії (`examples/stage3/03_astronomy.stdout.json`):

```
- Українська Wikipedia (uk): інтерес падає, −60 % (6 712 переглядів проти 16 614). Довіра: середня.
  - Уся uk.wikipedia за той самий час: −25 %; з поправкою на це зміна теми −46 %.
  - Разовий сплеск у вересні 2024: 4 687 переглядів, у 7,7 раза вище за медіану; без нього висновок той самий (−46 %).
  - Різка й стійка зміна рівня з червня 2025: з ~1 019 до ~361 на місяць. …
```

```bash
python3 scripts/analyze_trend.py --views views.json --out analysis.json
```

## Етап 4: звіт на одну сторінку (PDF)

`scripts/build_report.py` складає з аналізу етапу 3 сторінку A4, якою можна
поділитися. Він нічого не рахує заново, тож числа у звіті й у відповіді агента
однакові.

- **Зміст:** шапка з питанням користувача, головний висновок, таблиця по мовах
  (перегляди, зміна, зміна з поправкою на розділ, довіра), графік, причини
  рівня довіри, «що з цього випливає» і «припущення й обмеження».
- **Висновки для рішення** детерміновані: зростання з достатньою довірою —
  «кандидат для дослідження»; ±поріг — «стабільний інтерес»; падіння —
  «не пріоритет за цими даними»; низька довіра — «потрібна перевірка»; немає
  статті — «не виміряно, потрібні інші джерела».
- **Одна сторінка гарантовано:** якщо зміст не вміщується (напр., 8 мов),
  скрипт бере стисліший варіант верстки: менший шрифт, менше причин,
  нижчий графік.
- **Без залежностей:** `pdf_writer.py` сам пише PDF і вбудовує шрифт DejaVu Sans
  (лежить у `assets/fonts` разом з ліцензією) підмножиною лише використаних
  гліфів. Звіт важить 50–60 КБ замість ~800 КБ з цілим шрифтом. Текст можна
  шукати й копіювати: є таблиця ToUnicode.

```bash
python3 scripts/build_report.py --analysis analysis.json --views views.json \
  --out report.pdf --question "<питання користувача>"
```

## Файли, які створює навичка

Усе, що створюють скрипти, лягає в одну теку в робочій теці користувача:

```
wikipedia-interest-output/
├── .gitignore                 # «*» — навичка створює його сама, у git нічого не потрапляє
└── 20260927-150332-Q333/      # один запуск: дата-час і QID теми
    ├── basket.json            # етап 1: кошик статей
    ├── views.json             # етап 2: перегляди
    ├── analysis.json          # етап 3: аналіз
    ├── views.svg              # етап 3: графік
    └── report.pdf             # етап 4: звіт
```

`--out` агенту не потрібен: кожен скрипт повертає `next_command` — готову
команду наступного етапу з уже підставленими шляхами. Відповідь користувачу
закінчується блоком «Створено теку з результатами: <повний шлях>» з переліком
файлів і того, що в кожному. Інше місце —
`WIKIPEDIA_INTEREST_OUTPUT`. Якщо агент запустив скрипт із теки самої навички,
файли все одно не ляжуть поруч із кодом. Кеш відповідей API — окремо, у
`~/.cache/wikipedia-interest-analysis`.

## Етап 5: план розвитку

[`docs/roadmap.md`](roadmap.md)
описує, як розвивати навичку для складніших досліджень і більших обсягів
даних. Головний урок перевірки: правило в `SKILL.md` дешева модель виконує
ненадійно, а код — завжди. Тому всі ітерації переносять рішення в скрипти з
готовим текстом:

1. Перевірка висновків за даними самої Wikipedia: журнал перейменувань статті
   для зламів рівня, контрольний кошик стабільних статей.
2. Точніша статистика: сезонна декомпозиція, інтервал невизначеності для зміни.
3. Теми з кількох понять і мови без окремої статті (згадки як непрямий сигнал).
4. Власні критерії перспективності й серії запитів зі збереженим станом.
5. Більші обсяги: пакетний режим, дампи переглядів, інкрементальні оновлення.
6. Звіти для ширшої аудиторії: шрифти для інших письменностей, кілька сторінок.

І постійно — автоматизований регресійний прогін сценаріїв на дешевій моделі.

## Як перевіряли

Код написано за допомогою AI-асистента (Claude Code). Його результат
перевірявся на трьох рівнях.

1. **Реальні дані замість припущень.** Перед написанням логіки ми вручну
   дослідили відповіді Wikidata і Вікіпедії для прикладів із завдання. Так
   з'ясувалося, що:
   - у польській Вікіпедії немає статті про інтервальне голодування;
   - у астрономії 69 підкласів, тож автоматично додавати пов'язані поняття
     не можна;

     English», тому потрібне друге, англійське формулювання;
   - QID, запропонований в одній із чернеток іншим AI-асистентом (Q911526),
     неправильний: справжній — Q1666254.

   Твердження AI ми звіряли з API. Наприклад, польська стаття «Głodówka

## Відомі обмеження етапу 1

- **Прізвища без імені** («Шевченко»). Пошук Wikidata не повертає людей, лише
  селища й елемент «прізвище», тож агент може підставити кандидата сам.
  Пріоритет низький: для вибору теми чи мови продукту користувачі питають про
  поняття, а людину зазвичай називають повністю.
- **Схожі поняття поза структурою Wikidata** (як «Głodówka lecznicza»)
  автоматично не знаходяться.
- **Список пов'язаних понять неповний.** На одну властивість перевіряється
  не більше 50 понять (`related_truncated`).
- **Мова відповіді.** Дешева модель інколи вставляє в українську відповідь
  окремі слова іншими мовами.
